Document intent
This document translates the assigned project brief and its visual reference into a buildable, testable frontend project. It separates the assignment’s explicit requirements from recommended interface enhancements and records the limits of a browser-only demonstration.

1. Technical Overview
This specification defines the implementation approach for the Campus Lost and Found frontend. The application is a static, single-page-style website built with semantic HTML5, CSS3, and Vanilla JavaScript. Browser LocalStorage provides persistence for demonstration data.
Non-negotiable constraint  Do not use a JavaScript framework, CSS framework, component library, utility library, backend, database, external API, package manager, or third-party runtime dependency.

4. Application Architecture
4.1 Logical Layers
Layer
Responsibilities

Renders page sections, item cards, counts, filter states, forms, notifications, and dialogs.

Holds current tab, search text, selected category/location, current detail item, active local profile email, and loaded records.
Domain logic
Applies filters, validates inputs, creates report/claim records, calculates statuses, and enforces field rules.
Persistence adapter
Loads, parses, saves, and safely removes JSON values from LocalStorage.
Seed data
Supplies example listings when the browser has no existing item dataset.

4.2 Data Flow
On startup, read versioned LocalStorage keys and validate parsed data shapes.
If no item dataset exists, create the sample item collection once and persist it.
Initialize the in-memory application state from the loaded records.
Render the board and attach delegated event listeners.
When the user changes a filter, derive visible records from state and re-render the results area.
When the user submits a report or claim, validate the form, create a record, update state, persist it, and update the relevant views.

6. LocalStorage Specification
Key
Stored value
Behavior
clf.items.v1
JSON array of Item records
Read on startup; seed only when key is absent or has no valid dataset; update after report creation/deletion.
clf.claims.v1
JSON array of Claim records
Read on startup; append on claim submission; update only through explicit demo behavior if implemented.
clf.profile.v1
JSON object containing currentEmail
Used only to filter the My Reports screen locally.

Wrap JSON.parse and JSON.stringify operations in try/catch.
Validate expected arrays and required fields before accepting stored data.
If stored JSON is malformed, show a recoverable message and offer a “Reset demo data” action rather than crashing.
Do not overwrite valid user-created data during normal initialization.
Handle quota errors when saving images or records; show an actionable error and allow the user to retry without the image.
Provide a clearly labeled reset option for the demonstration that removes only the application keys listed above.

8. Filtering and Search Logic
Create one pure filtering function that receives the full item array and current filter state. Apply filters in a predictable sequence: active tab, category, location, then keyword. Search should be case-insensitive and trim leading/trailing whitespace.
Keyword fields: itemName and description; optionally include specificSpot if useful, but do not search private contact information.
Location field: exact selected campus location or an “All locations” option. If free-text location search is chosen instead of a dropdown, match case-insensitively against location and specificSpot.
Category field: exact enum match or All Categories.
Clear Filters resets keyword, category, and location while retaining the currently selected Lost/Found tab.
Display a result count and a clear no-results state.

9.1 Item Report
Field
Validation

Required; only Lost or Found.
Item name
Required after trimming; max 100 characters recommended.
Category
Required; one of the configured categories.
Location
Required; choose or enter a campus location.
Date
Required valid date; no future date in the standard flow.
Contact info
Required; validate email format if campus email is selected as the supported format.
Description / specific spot
Optional; trim whitespace and enforce max lengths.
Photo
Optional; only JPG/JPEG/PNG, maximum 5 MB before compression.

9.2 Claim Request
Only found items in a claimable state should offer Claim This Item.
Name, contact/email, and identifying detail are required.
A claim submission creates a new unique claim ID and starts in pending_verification.
After submission, display the claim ID and local confirmation; do not say that an email was sent or that ownership was verified.
9.3 Image Handling
Validate both MIME type and filename extension; do not trust extension alone.
Display a local preview before submission.
Recommended: use a Canvas to resize the longest edge to approximately 1200 px and encode a compressed JPEG for LocalStorage.
Keep the original input limit at 5 MB as shown in the design reference. If saving still exceeds LocalStorage quota, offer a retry without the image.
Provide meaningful alt text for item images or empty alt text for decorative images.

11. Security, Privacy, and Data Handling
Do not use innerHTML with untrusted user-entered strings. Prefer createElement and textContent; if templating is unavoidable, escape all user-provided values.
Do not display contactEmail on public item cards or public item details.
LocalStorage is accessible to scripts running on the same origin and to people with access to the browser profile. It is not encrypted, authenticated, or appropriate for sensitive personal data.
Do not request or store student ID numbers, passwords, government IDs, payment details, or photos of sensitive documents.
Do not claim that campus emails are verified. Email syntax validation is not identity verification.
No network requests should be made by the application. User data stays in the local browser unless the hosting environment itself provides unrelated static-file access.

13. Error Handling and Empty States
No results: explain that no items match and provide Clear Filters.
No reports: prompt the user to submit a lost or found report.
Invalid form: show field-level messages and focus the first invalid field.
Storage read failure: load a safe empty/sample state and explain that browser storage could not be read.
Storage write/quota failure: preserve form values, show an error, and offer retry without optional image data.
Missing image: use a local fallback visual; never show a broken image icon.
Deleted report: require confirmation and show a success message after persistence succeeds.

15. Definition of Done
All four Excel core requirements are implemented and pass their acceptance checks.
The reference-aligned screens and interactions included in scope are functional, not static mockups.
No prohibited framework or library is present in source files.
All user-generated values are rendered safely and contact information is hidden from public listing views.
LocalStorage initialization, persistence, malformed-data handling, and reset behavior are tested.
The site is responsive, keyboard-usable, and free of obvious console errors during the test checklist.
README explains how to run the static site and clearly states browser-only limitations.
16. Implementation Notes and Open Decisions
The campus name and contact email must be treated as configurable sample content unless the project owner supplies official values.
The source spreadsheet does not prescribe the exact campus location list, report ID format, statuses, or image compression behavior; those details are implementation decisions documented here.
The PDF shows an image upload hint of JPG or PNG up to 5 MB; this is used as the recommended upload limit.
No actual claim-review interface is mandated by the Excel row. If one is added for demonstration, it must be clearly labeled as simulated and must not imply a real staff workflow.
